# ef_first_cn_AA.dll — 静态结构分析与运行时补丁机制

分析对象：`/home/lrxin/Downloads/ef - the first tale/` 目录下的 `ef_first_cn_AA.dll`
（260,200 字节）——即 "ef - the first tale" 英文/全年龄版（`ef_first_AA.exe`、
`ef_first_en_AA.chm`）的简体中文化组件。

本文所有结论都标注 **实测（observed）**（直接读取字节 / 经实际运行验证）或
**推断（inferred）**（基于证据推理）。分析过程中从未修改游戏文件；该 DLL 仅在
`analysis/dll/wine/` 下的**副本**上运行过（Wine 10.0），用于抓取打过补丁的内存镜像。

---

## 0. 摘要（TL;DR）

**它是什么（实测）：** 一个体积很小、带数字签名的辅助 DLL，被改过的游戏主程序
`ef_first_AA.exe` **静态导入**（导入模块名 `ef_first_cn_AA.dll`，导入符号 `DirA`）。
它**没有代理 DLL 导出**（没有 `Direct3DCreate9` / `DirectDrawCreate` /
`DirectInput8Create` / version API），**没有 TLS 回调**，**不是注入到别的进程的代码**，
也**不包含剧情文本或图片**（只有 2 张与 exe 内位图逐字节相同的小 UI 位图、2 个本地化
对话框、2 个本地化字符串表）。

**它做什么（实测）：** 它的 `DllMain`（`DLL_PROCESS_ATTACH`）通过
`GetModuleHandleW(NULL)` 找到宿主 exe，然后**在内存中给已加载的 exe 镜像打补丁**
（`VirtualProtect` + 直接写字节 + 改写调用点 + 改写 IAT）。这些补丁在引擎行为层面
实现中文化：

1. **UI 字符串与角色名**：把 exe `.rdata` 中 19 条写死的英文弹出菜单标签替换成 GBK
   中文；把 exe `.data` 中 10 个写死的角色名指针替换为指向 DLL 内 GBK 名字的指针；
   把默认字体名 `"Merriweather MG"` 替换为 `"黑体"`（SimHei），并把字体示例文本换成
   中文示例。
2. **对话框/字符串重定向**：把 exe 的 USER32 IAT 中 `LoadStringA` 与
   `DialogBoxParamA` 两项挂钩到 DLL 包装函数，包装函数把 hInstance 由 exe 换成 DLL，
   于是游戏的消息字符串来自 DLL 的中文 `RT_STRING` 块 7/8、对话框（关于 `#103`、
   存档备注 `#139`）也来自 DLL，而不是 exe 的英文版本。
3. **文本引擎 Shift-JIS → GBK 适配**：约 40 处代码字节补丁，改 exe 的文本相关代码
   （前导字节界限 `0x9F→0xFE`、绕过 SJIS 特殊符号表、重写字形码映射、
   `MultiByteToWideChar` 代码页 `1252→936` 且输入长度 1→2 字节、GBK 感知的字符读取
   hook、字体枚举过滤改动）。
4. **数据目录重定向**：把"成人（r18）补丁安装目录"的注册表查询替换为 `.\r18_cn`
   （仅当该目录存在时），把"存档目录"解析替换为 `.\save_cn\`。
5. **资源提供**：通过第 2 点的 hInstance 交换，使用 DLL 自己 `.rsrc` 中的中文字符串/
   对话框；那 2 张位图就是对话框背景图。

**它不做什么（实测/对移植很重要）：** 它完全不处理 `.paz`/脚本（没有这类字符串和
导入），不加载也不替换内嵌字体，不写文件，不碰游戏数据。真正的中文剧情文本、图片
文字与成人内容都在 PAZ 归档和 `r18_cn/` 里；DLL 只修补引擎与 exe 的 UI，并重定向
目录。

**加载机制（实测）：** 分发的 `ef_first_AA.exe` 被*离线*修改过：在第 15 个导入描述符
中追加了 `ef_first_cn_AA.dll!DirA`（旧导入描述符表留在 RVA `0x1A3D5C` 处作废，
`PADDINGXXPADDING` 标记位于 RVA `0x22B5F0`，导入目录项被改指到 RVA `0x22B600`，
PE 校验和保持过期未更新）。随后 exe 被重新签名，其 Authenticode 签名对**这些修改后的
字节仍然有效**（当前镜像的计算摘要与签名摘要一致；RFC3161 时间戳 2024-12-16）。
因此该静态导入属于随游戏分发的、已签名的产物：Windows 在游戏运行前加载 DLL，
`DllMain` 完成打补丁，而 `DirA`（一个空壳 `ret 0`）从不被代码调用。

**来源/溯源（实测）：** exe 与 DLL 都带有 **Japan Animation Contents, Inc.**（日本
东京）的、经 Sectigo Public Code Signing 证书链签发的有效 Authenticode 签名，时间戳
均为 2024-12-16。exe 版本资源仍写着 `minori / No Name Losers / MangaGamer`，
FileVersion 1.9.0.1，OriginalFilename `ef_first_en.exe`；其 PE 时间戳为 2019-08-11，
英文 CHM 手册编译于 2019-08-10。DLL 构建于 2024-12-13。整体看，这是 2019 年英文/
全年龄版在 2024 年 12 月被重新打包的"授权/官方"简体中文版（确切的授权与版本状态
**未知**）。

## 3. DLL 是如何被加载的（实测）

### 3.1 exe 被离线修改以导入该 DLL

分发的 `ef_first_AA.exe` 共导入 **14** 个 DLL，最后一个是 `ef_first_cn_AA.dll`
（导入符号 `DirA`）。原始导入描述符表仍残留在 RVA `0x1A3D5C` 处（已作废）。补丁工具
在 `.rsrc` 节尾部追加了一张新表：

| exe RVA | 字节 | 含义 |
|---|---|---|
| `0x22B5F0` | `"PADDINGXXPADDING"` | 16 字节工具标记（打补丁工具的填充） |
| `0x22B600` | 15 个 20 字节 `IMAGE_IMPORT_DESCRIPTOR`（13 个原有 + ef_first_cn + null）；导入数据目录大小 = 0x12C | 新的导入目录 |
| `0x22B704` | 描述符 #13：OFT/FT = `0x22B740`，Name = `0x22B748` | ef_first_cn_AA.dll 的描述符 |
| `0x22B730` | 全零描述符 | 终止符 |
| `0x22B740` | DWORD `0x22B75B`（thunk），加载时被解析为 `DLL+0x1DA0` | `DirA` 的 IAT 槽 |
| `0x22B748` | `"ef_first_cn_AA.dll"` | 被导入的模块名 |
| `0x22B75B` | hint `0x0001`、`"DirA"` | hint/name |

离线修改的证据：PE 校验和存储值 `0x1FCB9B` vs 重算值 `0x1FE1AE`（过期）；文件偏移
`0x190` 处的导入数据目录项被改指到 `0x22B600/0x12C`；`0x1A3D5C` 的旧描述符表已不再被
引用；以及 `PADDINGXXPADDING` 标记。

因为这是静态导入，`ef_first_cn_AA.dll` 必须存在，否则 exe 无法启动——该导入**存在的
唯一目的就是强制加载 DLL**：

* `DirA` 是空壳（`ret 0`）；
* exe 中没有任何指令引用 `DirA` 的 IAT 槽（VA `0x62B740`）——全镜像搜索，0 处交叉引用；
* 真正的全部工作在 `DllMain` 中完成。

签名情况（§8）表明：该导入是在 2024-12-16 签名**之前**加入的，即已签名的产物本身
就包含这个 DLL 导入；不存在运行时加载（没有 `LoadLibrary` 调用，也没有针对该 DLL 的
配置/注册表触发机制）。

### 3.2 DllMain 行为（由反汇编 + Wine 内存 diff 实测）

`DllMain` → `0x1B30`：
1. 两次 `GetModuleHandleW(NULL)` → exe 基址 `0x400000`；把 DLL hInstance 与 exe 基址
   写入 `.data` 全局变量（供两个包装函数使用）。
2. 调用 `0x1570`（修改文本/字形相关代码；见 §4/§5）。
3. 直接再应用约 20 处补丁（菜单字符串、角色名指针、字体名、字体示例、存档/r18 hook、
   字符读取 hook、IAT hook）。
4. 返回 TRUE；游戏带着已打补丁的镜像继续运行。

游戏之后再也见不到未打补丁的字符串/代码：例如运行时镜像的 `.data` 中出现
`"黑体\0weather MG"`（游戏复制了已被修补的字体名字符串）、以及 hook 生成的
`"r18_cn\"` 路径缓冲区——这证实补丁发生在游戏初始化之前。

| exe RVA | 变更 | 疑似引擎作用 |

## 5. 字体与文本渲染管线（移植最关心的部分）

exe 自己用 **GDI32** 渲染全部文本（12 个导入，实测）：
`CreateFontA`、`AddFontMemResourceEx`、`RemoveFontMemResourceEx`、`EnumFontFamiliesExA`、
`SelectObject`、`GetGlyphOutlineW`、`GetGlyphOutlineA`、`GetCharWidth32A`、
`GetTextMetricsA`、`CreateCompatibleDC`、`DeleteDC`、`DeleteObject`。

实测到的调用点：

| exe RVA | GDI 调用/动作 | 作用 |
|---|---|---|
| `0x1253BE` | `AddFontMemResourceEx` | 注册 exe 的内嵌字体（RCDATA 162 = 28,432 字节 TrueType 子集 `"Merriweather MG"`，仅拉丁字符；sfnt 表：OS/2、cmap、glyf、head、hhea、hmtx、kern、loca、maxp、morx、name、post、prep） |
| `0x124F69` | `CreateFontA`（从 `esi+0xC..0x38` 的字体对象压入 14 个参数） | 创建游戏内字体；字体名 = 被补丁改过的默认字符串 |
| `0x124F94/0x124FA2` | `SelectObject`、`GetTextMetricsA` | 字体度量初始化 |
| `0x53F226` + 回调 `0x53F0F0` | `EnumFontFamiliesExA` | 系统设置里的字体下拉框枚举；回调受 `0x13F150/0x13F16A` 两处补丁影响 |
| `0x1250FD`、`0x12520B` | `GetGlyphOutlineW`（在 CP936 转换之后） | 比例字体逐字符字形轮廓/度量 |
| `0x124E07` | `GetGlyphOutlineA` | 旧的单字节字符路径 |
| `0x124E4F`、`0x11978F`、`0x11A1D1`、`0x11A20A` | `GetCharWidth32A` | 字符前进宽度（文本换行/测量） |

因此，渲染层面的汉化策略是：

1. **默认字体名** `Merriweather MG`（内嵌拉丁字体）**→ `黑体`（SimHei，系统 CJK 字体）**
   —— exe 仍为它的拉丁字体调用 `AddFontMemResourceEx`，但向 GDI 请求的是 `黑体`，
   GDI 解析到带 CJK 字形的系统字体。这里**没有替换字体资源**——内嵌 TTF 仍在，游戏
   也不随附 CJK 字体（必须由 Windows 提供 SimHei）。`save_cn/...\sysparams.txt`
   （实测，GBK 编码）显示了中文版实际配置：`fontname = 汉仪文黑-85W`、
   `symbolFontname = 黑体`。
2. **双字节 GBK 字符**由被 hook 的字符读取函数读出，用 `MultiByteToWideChar(CP = 936)`
   而不是 `CP = 1252` 转换，再交给 `GetGlyphOutlineW`；文本解析/测量/换行的界限从
   SJIS 前导字节上界 `0x9F` 改为 GBK 上界 `0xFE`。
3. 对话框/消息字符串以及"关于/存档"对话框，通过 `LoadStringA`/`DialogBoxParamA` 的
   hInstance 交换来自 DLL 资源（中文）。

**这意味着：** 中文版并没有改变渲染 API——它改变的是*引擎把文本字节按哪个代码页
解释*、*请求哪个字体名*、*由哪个资源实例提供字符串*。这些恰好都应是原生移植版以
数据/配置形式暴露的开关，而不是二进制打补丁。

## 6. 中文文本编码——哪些是 GBK、哪些不是（Lead 问题 2）

* **DLL 内的字面量（实测）：** DLL `.rdata` 中所有中文字节串都是 **GBK（CP936）**——
  例如 `存档 (&O)` = `B4 E6 B5 B5 20 28 26 4F 29`，`黑体` = `BA DA CC E5`。这些字节被
  原样写入 exe（此时已按 GBK 渲染）的字符串槽。
* **DLL 资源（实测）：** Win32 `RT_STRING`/`RT_DIALOG` 按格式本身就是 **UTF-16LE**；
  其中的中文是普通的 Unicode 中文（这是 Windows 资源的正常行为，不是补丁的编码选择）。
* **游戏内配置文件（实测）：** `save_cn/minori/ef - the first tale.(AA)/sysparams.txt`
  是 **GBK**（`汉仪文黑-85W`、`黑体` 均能按 GBK 正确解码）——即引擎以 ANSI 代码页
  读写自己的文本配置，而本版本该代码页就是 GBK。
* **PAZ 内的脚本/UI 文本（推断，未直接观测）：** 所有 PAZ 容器都是二进制归档，头几个
  字节是 ASCII 标记 `ef_first_en_AA\0`（成人数据为 `ef_first_en_AA_R18Patch\0`）；
  对 `scr.paz`、`st.paz`、`sys.paz`、`r18_cn/*.paz` 做朴素 GBK 扫描找不到明文
  （条目被压缩/打包），因此无法直接读出字面编码。它必须是 **GBK 的 ANSI 文本**，
  因为引擎文本管线现在正是在解析归档加载文本的那些点上按 GBK 解码（CP936 + 前导字节
  ≥0x81、上界 0xFE）。*归档层面的确认留给归档分析同事（需要解包 PAZ）。*
* **手册/CHM 只有英文**（不随附中文手册）；用户侧的 `中文攻略.txt` 是单独的 UTF-8
  文本文件，引擎不读取它。

## 9. 移植结论——还需要这个 DLL 吗？（Lead 问题 4）

**不需要。** 对 Linux 原生移植，该 DLL 及其整套补丁层应当**全部丢弃**；一旦引擎以
原生方式实现同样功能，DLL 里没有任何东西是必需的。拆分如下：

### 数据层（保留/沿用）
* 带中文文本/UI 的 PAZ 归档（编码：GBK —— 在导入时解码或离线转成 UTF-8），以及媒体
  归档；`r18_cn/*` 作为成人内容数据集；`save_cn/` 存档槽布局与 `sysparams.txt` 格式
  （GBK 键值、制表符分隔；注意中文版配置还含有英文手册里没有的键：`bltOnce`、
  `modeNNL`、`stretchAA`、`symbolFontname` 等）。
* UI 美术（两张对话框位图在 exe 和 DLL 中都存在，内容相同）。

### 需要原生重实现的代码层（而不是给 exe 打补丁）
| DLL/补丁行为 | 原生实现方式 |
|---|---|
| 文本字节按 CP936 解码 + 双字节字符处理（`0x119CD7` hook、`0x125090…` 的 CP1252→936、15 处 `0x9F→0xFE` 界限、`0xCA6D0` 字形映射器、标点映射） | 把脚本/UI 文本按 **GBK** 解码（或离线把归档转成 UTF-8）；用 Unicode 字符做排版/渲染；从字体实现 CJK 双字节字符前进宽度、CJK 换行/禁则处理；不需要 SJIS 特殊分支 |
| 默认字体 `Merriweather MG → 黑体`（`0x15FE34`）、字体枚举过滤补丁（`0x13F150/0x13F16A`） | 打包/配置一款 **CJK 字体**（Noto Sans CJK SC 授权安全；中文版配置用的是 汉仪文黑-85W 与 黑体，二者均为商业字体）；用 FreeType/HarfBuzz/SDL_ttf 渲染；把 `fontname`/`symbolFontname` 暴露为配置 |
| exe `.rdata` 中的 UI 标签与角色名被就地替换 | 把所有 UI 字符串 + 10 个角色名移到外部本地化文件（JSON/PO）；不需要改代码；角色名表变成数据 |
| `LoadStringA`/`DialogBoxParamA` 的 hInstance 交换 → DLL 资源 | 从本地化资源包正常加载资源（或更简单地用外部资源/配置文件）；"关于"与存档备注对话框用移植版的 UI 工具包重新实现 |
| 存档目录 hook（`0xC3735`）→ `save_cn\` | 直接把 `<gamedir>/save_cn` 用作存档目录（路径即配置） |
| r18 安装目录 hook（`0xBDC88B`）→ 存在即用 `r18_cn` | 检测 `<gamedir>/r18_cn` 目录来决定是否启用成人内容（不用注册表） |
| exe 中对 `ef_first_cn_AA.dll!DirA` 的静态导入 | 重建/移植 exe 时删除该导入；不需要 DLL |
| CHM 帮助（`ef_first_en_AA.chm`，从"帮助"菜单打开） | 可选：移植版可随附从 `chm_extract/` 提取的 HTML，或直接去掉帮助；手册只有英文 |

**不要**把 DLL 本身、`PADDINGXXPADDING` 导入 hack、IAT hook、或内存中的 `.rdata`
字节补丁搬进移植版——它们只是"拿不到引擎源码"时的权宜之计。移植版必须实现的
引擎级功能是：*GBK/Unicode 文本管线*、*CJK 字体 + 字形度量*、*CJK 换行*、
*本地化资源字符串/对话框*、*数据目录配置*，以及*可选的一个英文手册查看器*。

## 11. 未知项/局限（诚实清单）

1. **PAZ 脚本编码未直接验证** —— 归档被压缩/打包；GBK 是由引擎补丁和 GBK 配置文件
   推断出来的。需要解包归档（归档分析同事的任务）来确认脚本文节编码。
2. **字体枚举过滤的确切语义**（`0x13F150`、`0x13F16A`）—— `EnumFontFamiliesExA` 回调
